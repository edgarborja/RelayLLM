# Architecture and transport decision

```
 Browser (static site)                     Public Nostr relays                  Your machine
 ┌──────────────────────┐                 ┌───────────────────┐              ┌──────────────────────────┐
 │ RelayLLM client      │  wss (out)      │  relay A          │  wss (out)   │ RelayLLM worker          │
 │  identity vault      │ ──────────────▶ │  relay B          │ ◀─────────── │  transport → auth →      │
 │  IndexedDB (encrypt.)│ ◀────────────── │  (store nothing   │ ───────────▶ │  router → provider       │──▶ LM Studio / Bionic
 │  WorkerClient        │   kind 21059    │   readable)       │  kind 21059  │  adapter (loopback only) │    Ollama / vLLM
 └──────────────────────┘                 └───────────────────┘              └──────────────────────────┘
```

Both sides only make **outbound** WebSocket connections to relays. The worker
needs no open port, public IP, VPN, or reverse proxy.

## Components

| Package | Role |
|---|---|
| `packages/protocol` | Versioned message schemas (zod), validation, envelope helpers, error codes |
| `packages/nostr-transport` | Encryption/wrapping, relay pool, replay protection, fragmentation, pairing links, `WorkerClient` |
| `packages/provider-adapters` | `ProviderAdapter` interface; LM Studio, Ollama, vLLM, generic OpenAI-compatible adapters |
| `packages/test-utils` | Mock relay and mock OpenAI-compatible server for tests and local development |
| `apps/worker` | CLI, config, secret storage, access control, request gateway |
| `apps/client` | React + Vite static web app |

Request path in the worker:
`RelayPool → NostrEndpoint (unwrap, verify, replay check, reassemble) → Gateway (validate, authorize, rate-limit) → ProviderAdapter → local HTTP API`.

## Research summary

| Option | Verdict |
|---|---|
| **NIP-44 v2** | Used. Audited, versioned, authenticated encryption with padding. Plaintext limit is 65,535 bytes, which drives fragmentation. |
| **NIP-17 / NIP-59 gift wrap** | Used in modified form. NIP-59's rumor → seal → wrap has three layers and randomizes `created_at` by up to two days. That breaks `since` filters for live streaming and adds overhead to every chunk. We keep the essential property (a random outer key, so relays don't learn the sender) with one fewer layer: a *signed* inner event is NIP-44-encrypted inside a wrap. This matches ContextVM's CEP-4. |
| **ContextVM** (`@contextvm/sdk`) | Studied, not used as a dependency. It's a good fit conceptually: ephemeral kind 25910 messages, NIP-44 gift wraps (kind 1059/21059), and CEP-41 streaming with chunk indexes and `abort`. Reasons not to depend on it: the spec is a draft; it's built around MCP (JSON-RPC tool calls plus a mandatory final response); the SDK is LGPL/GPL; and muxll, its LLM proof of concept, needs Bun and doesn't cancel upstream generation. We adopt its conventions instead: kind 21059 ephemeral wrap, signed inner event, sequence-numbered chunks, abort. |
| **NIP-90 (DVMs)** | Not used for the MVP. DVM job results are public by default, encrypted DVM requests are poorly standardized, and there's no streaming or cancellation model. A NIP-90 facade could be added later without touching the core. |

## Wire format

```
outer: kind 21059 (ephemeral gift wrap), pubkey = fresh random key per event
       tags: ["p", <recipient>], ["expiration", <unix>]          (NIP-40)
       content: NIP-44( JSON(inner), random key ↔ recipient )

inner: kind 25920, pubkey = real sender, signed (Schnorr)
       tags: ["p", <recipient>]          ← binds the message to one recipient
       content: JSON application message (see protocol.md)
```

Ephemeral kinds (20000–29999) are forwarded to live subscribers but not
stored by relays. Lost events are recovered at the application layer
(`chat.resume`). Nothing depends on relay storage.

### Reply keys

Every request carries `replyTo`, a per-tab session key generated by the
client. The worker encrypts responses to that key. Benefits:

* The user's long-term pubkey never appears in relay-visible tags.
* NIP-07 extension users sign a request once, instead of approving a decryption for every streamed chunk.
* Relay AUTH (NIP-42) is answered with the session key, not the identity.

The `replyTo` value is inside the signed, encrypted request, so only the authenticated user can choose it.

### Streaming

The worker batches provider tokens and publishes `chat.delta` roughly every
250 ms, or sooner once 4,000 characters accumulate. At most one publish per
stream is in flight; while a publish is pending, new text coalesces into the
next batch. This provides backpressure without unbounded queues. Each delta has
a `seq`, and `chat.complete` carries `deltaCount` and `contentLength`.

The client reorders and de-duplicates by `seq`. A gap that persists for 2.5 s
triggers `chat.resume { missing: [...] }`. A stall or a relay reconnect
triggers `chat.resume { fromSeq }`. The worker keeps each finished transcript
for 3 minutes to serve these requests.

### Large requests

If a serialized message is larger than about 32 KB, the transport splits it
into `frag` messages. Each fragment is individually signed, wrapped, and
replay-checked. The receiver reassembles under limits: at most 64 fragments,
at most 1 MB, a 60 s deadline, and at most 4 pending messages per sender. It
then verifies a SHA-256 over the whole text. The worker only reassembles
fragments from senders who are allowed to send requests.

## Measured behavior

Measured with Bionic (qwen3.5-9b, Apple Silicon) and `wss://relay.k1.sv`:

* Request round trip (`server.info`): ~470 ms
* First visible text: ~1 s after sending
* Updates arrive about every 250 ms (145 updates in 37 s)
* Cancellation stops engine generation about one relay round trip after the user clicks stop.

Relays enforce their own rate and size limits. A congested or distant relay
makes streaming visibly chunkier; the client says so in the composer footer
while streaming. Use two or three nearby relays for redundancy.
